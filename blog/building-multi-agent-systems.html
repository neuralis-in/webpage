Building production-grade multi-agent systems.

The leap from a demo agent to a production agent isn't engineering. It's architectural surrender — to the unbounded ways an LLM in a loop can fail your business.

Dev Roy 14 May 2026 9 min read

Most agent demos are linear: take a prompt, call a tool, return an answer. Production agents are concurrent, recoverable, observable, and bounded. The gap between the two isn't in the model. It's in everything around it — and that everything is where the engineering actually lives.

We've built agentic systems for DevOps automation, research workflows, financial operations, and customer support. The architectural patterns that survive contact with production look almost nothing like the diagrams in agent-framework blog posts. Here's what we've learned.

The myth of the autonomous agent

The word "autonomous" has done real architectural damage. Teams hear it and reach for unsupervised loops — "let the agent figure it out" — without considering what that actually means when the agent can touch databases, deploy code, or move money.

Autonomy in production isn't unsupervised reasoning. It's bounded delegation. A production agent has four constraints that the demo agent does not:

  • A scope. What can it see, touch, modify? Encoded at the capability layer, not the prompt layer.
  • A budget. Tokens, dollars, wall-clock, tool calls. Enforced by the runtime, not requested by the prompt.
  • A verifier. What must be true when the agent claims success? Often a second model, sometimes deterministic code, never the agent itself.
  • An escape hatch. Where do humans take over? When? How? Defined before the agent runs.

Without these, you don't have an agent. You have an LLM in a loop with credentials.

The planner pattern is the only one that ships

Single-prompt agents fail at three things: long-horizon tasks, branched decision trees, and recovery from mid-execution errors. We've watched promising prototypes die at all three.

The planner pattern decouples reasoning from execution. It's not novel — it predates LLMs by decades — but in our experience it's the only architecture that scales past 12 steps without compounding errors:

  1. A planner LLM proposes a structured plan — typed JSON, not free text — describing each step's tool, inputs, and expected output.
  2. An executor (deterministic code, not the LLM) runs each step. The agent never directly invokes side effects.
  3. A verifier checks postconditions after each step. Did the expected file get written? Did the row count match? Did the response schema validate?
  4. On failure, the planner is invoked again — with the partial state, the error, and the original goal — and produces a corrective plan.

Harder to build than chaining tool calls. Slower per step. The only architecture we've seen survive a real long-running production workload.

Memory is not a vector database

Treating memory as "embed everything, retrieve top-K" is the most over-deployed anti-pattern in production agent design. It conflates three fundamentally different memory needs into a single retrieval primitive that's wrong for most of them.

Real production memory has tiers:

  • Working memory. The current execution context. Lives in the agent's prompt window. Short-lived. Gets compacted aggressively.
  • Episodic memory. A structured log of past tasks — what was asked, what was done, what worked, what failed. Queried by task type, user, time. This is SQL territory, not vectors.
  • Semantic memory. Long-tail facts the agent has accumulated. This is where vectors belong, but with hybrid retrieval (BM25 + embeddings) and reranking.

Conflating these into one "memory" abstraction will eat your context window and your error budget simultaneously. We keep them in three different stores with three different query patterns.

Guardrails are architecture, not validation

Output validation runs after the model finishes. Guardrails interrupt mid-stream. The difference matters enormously when your agent has tool access.

Production guardrails we ship with every agentic system:

  • Capability gating. The agent can't even see tools it shouldn't use for a given user, context, or scope. Removed from the tool manifest upstream of the model. Cheaper than refusal, more robust than prompting.
  • Mid-stream cancellation. Token-level monitors that stop generation when policy-violating content (PII, credentials, prohibited entities) appears. Backed by deterministic detectors, not another LLM.
  • Dry-run previews. Every state-changing tool call returns a preview the agent must explicitly confirm before the side effect lands. Useful for migrations, deployments, file writes, payments.
  • Step-level rate limits. Per-tool budgets that prevent runaway loops. Set per-user, per-session, per-environment.

Validation says "this output was bad." Guardrails ensure the bad output never had reach.

Observability is not "log the prompts"

Logging the prompt and the response is the floor, not the ceiling. Production agent observability needs to answer questions like: why did the agent take seven steps when three were sufficient? Why did it hallucinate this tool argument? Which step in the plan failed and what did the verifier say?

The minimum surface area for production agent traces:

  • The full plan tree, including revisions after failures.
  • Per-step tool inputs, outputs, and verifier results.
  • Per-step cost and latency, both in tokens and wall-clock.
  • Counterfactual breadcrumbs — what tools were considered and not selected at each decision point.
  • User feedback tied back to specific steps, not just the final output.

We've ended up building a custom trace UI on top of OpenTelemetry for most of our deployments. The off-the-shelf agent observability tools are catching up but still treat agents as request/response systems, which they aren't.

When NOT to use an agent

The hardest part of agentic engineering is knowing when not to do it.

If your problem has bounded inputs, deterministic logic, and clear success criteria — you don't need an agent. You need a function. We've watched teams reach for agentic frameworks to solve form validation problems. The framework is a tax you pay for non-determinism. Don't pay it unless you need it.

The right question isn't "can an agent do this?" It's "is the cost of non-determinism less than the cost of writing the logic explicitly?"

For most production workflows we ship, the answer is yes for orchestration, no for individual steps. An agent picks the strategy. Deterministic code executes it. The agent is the policy, not the runtime.

That separation — agent as orchestrator, code as executor — is what makes the whole system testable, debuggable, and ultimately ownable. Everything else we've described here flows from it.
