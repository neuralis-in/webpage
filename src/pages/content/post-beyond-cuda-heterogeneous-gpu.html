Beyond CUDA — the future of heterogeneous GPU computing.

CUDA has been the lingua franca of GPU compute for fifteen years. That's about to change — and code written today should be ready.

The Neuralis Team 21 April 2026 10 min read

For most of the last decade, "GPU compute" and "CUDA" were synonymous in the literature, in the curriculum, and in the recruiting funnel. That synonymy was always technically wrong — but it was practically true. If you wanted production-grade GPU performance, CUDA was the path.

It's becoming less practically true every quarter. AMD's MI300 series is shipping in real production deployments. Intel's Ponte Vecchio successors are appearing in HPC centers. Even more importantly, the abstraction layers that let kernels move between vendors are finally maturing.

The lock-in is real

CUDA's API is excellent. It's also proprietary to NVIDIA. Every CUDA kernel you write is a deepening commitment to NVIDIA hardware, NVIDIA pricing, NVIDIA driver compatibility, and — increasingly relevant — NVIDIA availability.

For most teams, this trade-off is fine. NVIDIA's hardware is best-in-class for ML, scientific simulation, and HPC. Their software stack is years ahead of the competition in tooling, profiling, and library ecosystem.

The assumption that this will remain true forever is not how serious infrastructure is built. We've watched at least three production deployments scramble in the past eighteen months because their CUDA-heavy stack collided with allocation, cost, or compliance constraints that made a vendor diversification mandatory.

The serious contenders

Three challengers worth taking seriously, each with a distinct strategy.

SYCL (and DPC++)

C++ kernels that compile to multiple backends. Code once, dispatch to NVIDIA, AMD, Intel, or even CPUs. Backed by Intel and the Khronos Group. Mature for HPC. Growing — fast — in ML.

SYCL is the closest thing to a vendor-neutral standard. The single-source C++ model means you keep your kernel code, your host code, and your build system all in one place. Performance is competitive with native CUDA for well-understood workloads.

ROCm + HIP

AMD's CUDA-equivalent stack. HIP is intentionally source-level compatible with most of CUDA's runtime API, which means existing CUDA kernels port with minimal changes. ROCm is the underlying runtime and library suite.

Real progress in the last eighteen months. On AMD's MI300 accelerators, native HIP code is competitive with — and sometimes exceeds — equivalent CUDA on NVIDIA hardware for certain workloads. The library coverage (rocBLAS, MIOpen, etc.) is closing the gap quickly.

oneAPI

Intel's umbrella over SYCL plus a comprehensive library ecosystem: oneMKL for linear algebra, oneDNN for deep learning, oneCCL for collective communication. The cross-vendor story is stronger here than anywhere else, because the libraries are designed from the start to dispatch to multiple backends.

Writing kernels that travel

The discipline of writing portable GPU code is the same discipline as writing portable systems code anywhere: code to what's standard, isolate what isn't.

  • Memory access patterns are universal. Coalesced loads are coalesced everywhere. Bank-conflict avoidance translates across vendors. These optimizations pay off no matter the target.
  • Warp/wavefront sizes differ. NVIDIA hardware uses 32, AMD's CDNA uses 64 (with newer architectures supporting 32 as well). Hardcode less, query more — warpSize or its equivalent exists in every dialect.
  • Tensor and matrix unit instructions are vendor-specific. Wrap them behind a unified interface. We use a small abstraction layer that dispatches to mma on NVIDIA, MFMA on AMD, XMX on Intel.
  • Atomics, barriers, shuffles have direct parallel implementations across vendors. Use portability libraries — Kokkos, RAJA, OCCA — rather than raw vendor intrinsics where you can.

The performance trade-off

Portable kernels are, on average, slower than hand-tuned vendor-specific kernels. The question isn't whether — the question is by how much, and whether it's worth it.

What we've measured across our own workloads:

  • On NVIDIA hardware, well-written SYCL is typically 5-15% slower than hand-tuned CUDA for most workloads, with the gap closing every release.
  • On AMD MI300, native HIP is typically 5-10% faster than HIP-translated CUDA. Native code on native hardware always wins by a small margin.
  • Library-heavy workloads (BLAS, FFT, sparse) often see no measurable gap — the vendor libraries dominate the kernel-level differences.

The question is whether single-digit-percent performance is worth the lock-in cost. For training a foundation model, the answer is often "yes, ship CUDA." For an HPC pipeline that needs to run on three different supercomputers, "no, ship SYCL."

What we're betting on

For new client engagements, our defaults look like this:

  • Portability-first workloads. SYCL or Kokkos, with vendor-specific paths for the 5% of kernels that need them.
  • Absolute-performance workloads. CUDA on NVIDIA, with the kernel abstraction designed so a future HIP/SYCL port is cheap if needed.
  • Mixed-vendor deployments. oneAPI for the library surface, SYCL for custom kernels, native runtimes only where they buy something we can't get otherwise.

We tell clients honestly which one their workload calls for. That conversation is usually more useful than the technology choice itself.

The interesting bet isn't on one ecosystem winning. It's on the abstraction layers maturing fast enough that the choice stops mattering.

We think that's a three-to-five-year horizon. Workloads architected today should be planning for the world where vendor choice is a deployment-time decision, not a compile-time one. That's a different mental model for a lot of teams — and it's the one we're building toward.
